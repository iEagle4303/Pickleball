# Stout Pickleball Club

A working university ladder league application built with Vue 3, TypeScript, Vite, Tailwind CSS v4, Vue Router, Pinia, Lucide, and Express. The browser communicates exclusively with the REST API. A local JSON store simulates the relational schema; no external database or service is required.

## Quick start

Use Node.js **22.12+ (22.x), 24+, or 26+** and npm.

```sh
npm install
npm run dev
```

Open **http://localhost:5173** or **http://127.0.0.1:5173**. The API runs at **http://127.0.0.1:3001**. The first API startup creates sample data if the JSON file is absent. A populated database is also included at `server/data/database.json`.

On Windows PowerShell, use `npm.cmd` if the system execution policy blocks `npm.ps1`. Run commands from this project's root.

## Available workflows

- **Clubhouse:** active league, real club totals, current leaderboard, recent scores, and suggested opponents.
- **Tournaments:** search and semester/status filters; create and edit; parent/child stages; overview, rankings, teams, games, and matchup tabs.
- **Team management:** create a team, edit its name/color as its creator or a team administrator, join an open spot, leave a team, and manage a doubles roster. Team creators can add other registered members. Teams support at most two players.
- **Results:** filter by team/tournament, sort by date or score, and add/edit/delete results with server-side validation and confirmation before deletion.
- **Rankings:** generated by the API from current tournament results, including wins, losses, games played, win percentage, and current players.
- **Matchups:** pair similar ranks, prefer opponents who have not recently played, rotate odd-team byes, and let tournament editors refresh recommendations. Pairings are suggestions, not scheduled events, and are not stored.
- **History:** completed tournaments by semester with their standings, participating teams, and results.
- **Accounts:** registration, login/logout, editable name/email, and permission management for authorized administrators.
- **Interface:** responsive sidebar/mobile navigation, persistent light/dark theme, keyboard focus, native accessible modal dialogs, notifications, and loading/error/empty states.

To add teams to a newly created tournament, open its **Teams** tab and choose **Manage teams**. Change its status to **In progress** before entering results. Scorers cannot create tournaments or delete results.

Historical results can be corrected by authorized coordinators. A team's historical wins/losses are scoped to the selected tournament; the team profile aggregates all appearances. Roster membership reflects the current relational UserTeam links, not a per-semester roster snapshot.

## Architecture

```text
client/src/
  features/
    home/           # Clubhouse page and its API module
    tournaments/    # Listing, details, editors, participant selection
    teams/          # Team profiles, editor, roster management
    games/          # History, result editor, shared result table
    rankings/       # Standings page and API-backed table/panel
    matchups/       # Recommended pairings and regeneration
    history/        # Completed-semester archive
    auth/           # Accounts, profile, permissions, Pinia auth store
  components/ui/    # Reusable buttons, dialogs, badges, states, avatars
  lib/              # Shared HTTP transport, formatting, async state, notifications
  router/           # Lazy page routes
server/src/
  controllers/      # HTTP response adapter
  routes/           # One router per resource; subroutes stay with their resource
  middleware/       # Session identification and authorization
  services/         # One service per route group; storage-independent business rules
    home/           # Clubhouse aggregation
    tournaments/    # Tournament CRUD, hierarchy, participating teams
    teams/          # Team CRUD and membership
    games/          # Results, validation, game history
    auth/           # Registration, login, sessions
    users/          # User directory, profile, permission assignment
    permissions/    # Permission catalog
    mappers/        # API view models from targeted repository queries
    shared/         # Shared record lookup/404 helpers
    rankings/       # RankingAlgorithm, rankingService, selected algorithm
    matchups/       # MatchupAlgorithm, matchupService, selected algorithm
  repositories/
    interfaces/     # Entity repositories plus UnitOfWork
    json/           # JSON-only storage, IDs, and repository implementations
  types/            # Shared entity type re-export
shared/types.ts     # Entities, join relationships, API view models
```

Every frontend feature owns its API calls inside its own `api/` directory. Vue components call those modules; they do not call fetch or read database files. Feature components can be reused by other features without duplicating requests or business rules. The shared HTTP client only handles transport, JSON, authentication cookies, and errors.

Each route group has a dedicated service. `routes/api.ts` only mounts routers, and `services/createServices.ts` only wires their dependencies. Tournament game, ranking, and matchup subroutes delegate to those dedicated services.

Services depend on the `UnitOfWork` and entity repository interfaces. Read callbacks receive query-only repositories; write callbacks receive repositories scoped to an atomic transaction. Services request specific records, relations, and aggregates instead of reading or mutating a `Database` object. IDs and persistence belong to the adapters.

See [the repository boundary and SQL adapter guide](server/src/repositories/README.md) for the migration contract.

### Replacing the ranking algorithm

1. Implement `RankingAlgorithm` from `server/src/services/rankings/RankingAlgorithm.ts`.
2. Select it by changing the import/assignment in `rankingService.ts`.
3. Run `npm run typecheck` and review the standings with sample game results.

The current placeholder sorts by **wins descending**, then **win percentage descending**, then **numeric team ID ascending** for deterministic exact ties. No-game teams receive a zero win percentage. The service filters games by tournament and adds player information. The frontend never sorts teams into ladder order or calculates rankings.

Matchups use the equivalent `MatchupAlgorithm`/`matchupService.ts` structure. The initial algorithm is deterministic for a given round. It greedily prefers nearby ranks and penalizes recent pairings; it is a recommendation heuristic, not a globally optimal tournament scheduler.

### JSON storage and SQL migration

`server/data/database.json` contains the eight requested relational tables as arrays:

`users`, `teams`, `permissions`, `tournaments`, `games`, `userTeams`, `userPermissions`, and `teamTournaments`, plus `sessions`.

The seed includes **18 users, eight teams, five tournaments across four semesters, a parent/child relationship, and 80 games** with valid participation links.

The tables intentionally share one JSON file so multi-table operations commit atomically. Writes are serialized, acquire a single-writer lock, write and sync a temporary file, then rename it over the prior snapshot. A rejected transaction never changes the stored snapshot. Database reads observe either the old or new complete file.

Run **one API writer process** for this development adapter. A second writer is rejected by the lock rather than silently losing data. After an unclean crash, verify no API process is running before removing a stale `database.json.lock` file. Do not edit the store while the server is running.

For SQL, implement the six entity repository interfaces with targeted queries and implement `UnitOfWork` using a connection and SQL transactions. Replace the JSON adapter construction in `index.ts`. Services and API view models remain unchanged; there is no requirement to load or rewrite all SQL tables. Only the JSON adapter and its seed generator use `JsonDatabase`, which is no longer a shared application type. Backups should include the whole JSON file. Never commit real member information or active session records.

Tournaments with results or children cannot be deleted. Teams with results cannot be removed from the corresponding tournament. Duplicate memberships/participations/permissions and cyclic parent relationships are rejected. Team statistics aggregate recorded results; division games are independent of their parent tournament.

## REST API

Successful responses use `{ "data": ... }`; failures use `{ "error": { "message": "...", "fields": { ... } } }` (fields are included for validation errors). Invalid input is 400, missing login 401, insufficient access 403, missing resources 404, and relationship/uniqueness conflicts 409.

| Method      | Endpoint                                              | Access                                                         |
| ----------- | ----------------------------------------------------- | -------------------------------------------------------------- |
| GET         | /api/health, /api/home                                | Public                                                         |
| GET         | /api/tournaments, /api/tournaments/:id                | Public                                                         |
| POST        | /api/tournaments                                      | CREATE_TOURNAMENT                                              |
| PUT, DELETE | /api/tournaments/:id                                  | EDIT_TOURNAMENT                                                |
| PUT         | /api/tournaments/:id/teams                            | EDIT_TOURNAMENT                                                |
| GET         | /api/tournaments/:id/games                            | Public                                                         |
| GET         | /api/tournaments/:id/rankings                         | Public                                                         |
| GET         | /api/tournaments/:id/matchups                         | Public                                                         |
| POST        | /api/tournaments/:id/matchups                         | EDIT_TOURNAMENT; body `{ "round": 1 }`                         |
| GET         | /api/teams, /api/teams/:id                            | Public                                                         |
| POST        | /api/teams                                            | Signed-in member                                               |
| PUT         | /api/teams/:id                                        | Team creator or MANAGE_TEAMS                                   |
| POST        | /api/teams/:id/members                                | Join self, or team creator/MANAGE_TEAMS adds member            |
| DELETE      | /api/teams/:id/members/:userID                        | Leave self, or team creator/MANAGE_TEAMS removes member        |
| GET         | /api/games?tournamentID=1&teamID=2                    | Public                                                         |
| POST        | /api/games                                            | ADD_GAME_RESULT                                                |
| PUT         | /api/games/:id                                        | EDIT_GAME_RESULT                                               |
| DELETE      | /api/games/:id                                        | DELETE_GAME_RESULT                                             |
| POST        | /api/auth/register, /api/auth/login, /api/auth/logout | Public                                                         |
| GET         | /api/auth/me                                          | Current account or null                                        |
| PUT         | /api/users/me                                         | Signed-in member                                               |
| GET         | /api/users                                            | Signed-in member; public member fields unless permission admin |
| GET         | /api/permissions                                      | MANAGE_PERMISSIONS                                             |
| PUT         | /api/users/:id/permissions                            | MANAGE_PERMISSIONS; body `{ "permissionIDs": [1, 2] }`         |

Result bodies include `tournamentID`, `winnerTeamID`, `loserTeamID`, integer `scoreWinner`/`scoreLoser`, and an ISO UTC `playedAt`. Both teams must exist and participate in the tournament, differ from each other, and have valid nonnegative scores with the winner ahead. Future-dated completed games and results for upcoming tournaments are rejected.

## Configuration

Copy `.env.example` to `.env` at the project root to override the API port, listening host, allowed browser origin, storage path, or runtime environment. Defaults work without a configuration file. Vite's development proxy targets port 3001; update `client/vite.config.ts` if you change the API port.

For an HTTPS deployment, set `NODE_ENV=production` to enable secure session cookies, set `CLIENT_ORIGIN` to the exact frontend origin, and select a new `DATA_FILE` outside version control. If creating a fresh store in production, set a private `SEED_PASSWORD` of at least 12 characters before startup. It affects new seed accounts only, never rewrites existing passwords. The supplied database and demo credentials are for local development.

The API applies Helmet headers, auth attempt limits, request size limits, origin/fetch-site checks for writes, server-side validation, and permission checks. It does not require a signing secret: opaque session tokens are randomly generated, stored only as hashes, and expire after seven days.
